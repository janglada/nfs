# Implementation Decisions

Rationale and trade-off notes for every significant design choice in this project.

---

## No application framework

**Decision**: Plain Java `main()`, no Spring / Quarkus / Micronaut.

**Why**: An NFS server is infrastructure code that runs for months or years.
Framework abstractions (dependency injection containers, annotation processors,
auto-configuration) add startup latency, reflection-heavy classpath scanning,
and subtle lifecycle ordering issues that are hard to debug at 3 AM when
storage is unavailable.

The total wiring code is ~25 lines in `NfsServer.java`. There is nothing to
gain from moving it into XML, YAML, or annotation magic. The `NfsServerConfig`
record provides a single, compile-checked place to adjust every parameter.

---

## nfs4j as the NFS library

**Decision**: Use dCache's [nfs4j](https://github.com/dCache/nfs4j) rather
than implementing the NFS protocol from scratch.

**Why**: The NFS protocol is complex. NFSv4.1 alone is a 617-page RFC. nfs4j
is a mature, production-tested library used in the dCache storage system (which
serves petabytes of HEP data for CERN). It handles:
- XDR encoding / decoding
- Session management (SEQUENCE, EXCHANGE_ID, CREATE_SESSION)
- Compound operation dispatch
- Locking semantics
- Callback channels

Our responsibility is a clean `VirtualFileSystem` implementation. nfs4j does
the protocol heavy-lifting.

**Trade-off**: nfs4j is not widely used outside the scientific storage world,
and its API surface is shaped by dCache's internal needs. The `Stat` object
has mutable setters rather than a builder, and some interface methods have
surprising defaults. These are minor irritants that do not affect correctness.

---

## Gradle migration from Maven

**Decision**: Migrate the build from Maven (`pom.xml`) to Gradle with the
version catalogue (`gradle/libs.versions.toml`).

**Why**:
- Gradle builds are incrementally cached by default, cutting CI times.
- The version catalogue (`libs.versions.toml`) centralises all dependency
  versions in one file, making upgrades a one-liner.
- Groovy DSL (`build.gradle`) is more concise than XML for expressing
  conditional compilation, custom tasks, and multi-project layouts.
- Gradle's daemon and configuration cache make repeated local builds faster
  than Maven's cold starts.

**Trade-off**: Gradle's own API evolves quickly and occasionally introduces
deprecation warnings. The `@Incubating` note in `build.gradle` (generated by
`gradle init`) is a reminder that the version catalogue API was still stabilising
at the time of creation.

## FileChannel over RandomAccessFile

**Decision**: `FileChannel.open(path, options)` instead of `new RandomAccessFile`.

**Why**:
- `FileChannel` is the modern NIO API. `RandomAccessFile` is a legacy class
  from Java 1.0 that wraps `FileDescriptor` without NIO interop.
- `FileChannel` supports positional reads (`read(buf, position)`) without
  moving a file pointer, which is important for concurrent access (multiple
  threads reading the same file at different offsets without synchronisation).
- `FileChannel.force(boolean)` maps directly to `fsync(2)` / `fdatasync(2)`,
  giving precise control over durability.
- `FileChannel` integrates with the `java.nio.channels` ecosystem (scatter/
  gather, memory-mapped files, file locks) if needed in the future.

---

## FileIoHandler — one channel per call

**Decision**: `FileIoHandler` opens a `FileChannel` for each read or write
call and closes it immediately.

**Why (initially)**: Simplicity and correctness. There is no shared state;
no risk of a stale channel being used after a rename or delete; no resource
leak if the server crashes mid-operation.

**Known limitation**: Opening a file descriptor is a syscall. For high-
throughput workloads (e.g. streaming large files via many small NFS read
operations), the fd open/close overhead can become measurable. A channel
pool (Caffeine cache keyed by `Path`) would eliminate this at the cost of
added lifecycle complexity.

The current design is intentionally simple. Profiling on a real workload
should determine whether pooling is worth adding.

---

## Stability level: always FILE_SYNC

**Decision**: `FileIoHandler.write()` returns `StabilityLevel.FILE_SYNC` and
calls `fc.force(false)` for all non-`UNSTABLE` writes.

**Why**: NFS write stability is a contract between the server and the client.
A server that returns `FILE_SYNC` promises that the data is on stable storage.
If the server returns `UNSTABLE` or `DATA_SYNC` and then crashes before a
`COMMIT` operation, the client must re-send the data. Most NFS clients will
reissue writes after a server reboot, but the reliability story is cleaner
if the server is always honest about durability.

**Trade-off**: `force(false)` issues `fdatasync(2)` on Linux, which is a
synchronous kernel call. On rotating disks this can be 5–10 ms. On SSDs it
is typically < 1 ms. For write-heavy workloads, grouping writes and issuing
one `fsync` per batch would improve throughput, but it would require a
more complex `FileIoHandler` that tracks pending writes per file.

---

## Caffeine over Guava or ConcurrentHashMap

**Decision**: Use [Caffeine](https://github.com/ben-manes/caffeine) for
in-process caching in `DbNfsIdMapping`.

**Why**:
- Caffeine is the successor to Guava's `LoadingCache`. Its W-TinyLFU eviction
  policy achieves near-optimal hit rates for NFS ID mapping access patterns
  (a small hot set of users).
- It provides `expireAfterWrite`, so stale entries are automatically evicted
  after the configured TTL — important when users are renamed or deleted in
  the database.
- A plain `ConcurrentHashMap` would require manual TTL management and
  separate eviction logic.
- Guava's cache is effectively feature-frozen; Caffeine is actively maintained.

---

## Bidirectional cache population

**Decision**: When `lookupByCode(code)` finds a DB row, it immediately
populates _both_ `byCode` (code → uid) and `byId` (uid → principal). And
vice versa for `lookupById`.

**Why**: NFS operations that create files call `principalToUid` (to fill
the stat for the new file). Shortly after, the client reads back the directory
listing and calls `uidToPrincipal` on the same user. Without cross-population,
the second call would be a cache miss and a second DB round-trip. With it,
one DB query warms both directions.

**Trade-off**: The two caches can momentarily be inconsistent if a user is
updated in the DB between the two lookups. Given the TTL-based eviction, the
window is bounded by `cacheExpiry`. For an NFS ID mapping use-case (rarely
changing user data), this is acceptable.

## Inode number from path hash

**Decision**: `PosixStatMapper.toStat()` computes the inode number as
`(long) path.toAbsolutePath().toString().hashCode() & 0xFFFFFFFFL`.

**Why**: NFS requires a stable, unique inode number per file. The actual
OS inode number (from `BasicFileAttributes.fileKey()`) would be ideal, but
`fileKey()` returns an opaque `Object` whose `Long` representation is only
accessible via internal Sun APIs on Linux. The path hash is a portable,
zero-overhead approximation.

**Known limitation**: Two files at different paths could theoretically
produce the same hash (32-bit hash over the full path string). In practice,
`String.hashCode()` distributes well enough for filesystem path strings that
collisions are rare in any real-world deployment. If collisions cause NFS
client confusion, the fix is to use `Files.getAttribute(path, "unix:ino")`
(Linux-specific) or the `sun.nio.fs.UnixFileKey` internal API.

See [inode-mapping.md](inode-mapping.md) for related discussion on handle
strategy.

## Pattern-matching switch for file type

**Decision**: `PosixStatMapper.typeMode()` uses a JDK 21 guarded
pattern-matching `switch` over `PosixFileAttributes`:

```java
return switch (attrs) {
    case PosixFileAttributes a when a.isDirectory()    -> Stat.S_IFDIR;
    case PosixFileAttributes a when a.isSymbolicLink() -> Stat.S_IFLNK;
    default                                            -> Stat.S_IFREG;
};
```

**Why**: This is idiomatic JDK 21+ code and makes the intent clear — we're
dispatching on a logical property of the type. A chain of `if`/`else if`
would work identically, but the `switch` makes exhaustiveness explicit and
compilers can warn if a case is unreachable.

**Trade-off**: JDK 17 (previous LTS) does not support guarded patterns in
`switch`. The project targets Java 21 source level, so this is safe. If
backporting to JDK 17 were needed, replace with an `if`/`else if` chain.

---

## GID delegates to UID

**Decision**: `principalToGid(p)` calls `principalToUid(p)`, and
`gidToPrincipal(gid)` calls `uidToPrincipal(gid)`.

**Why**: This server stores one identity per person in `sys_user`. Many
simple multi-user deployments have a 1:1 relationship between users and their
primary group (UIDs and GIDs match). Sharing the same lookup table simplifies
the schema while remaining correct for this model.

**Limitation**: True POSIX group semantics (one user in many groups, many
users in one group) are not supported. A production system with complex
group policies would need a separate `sys_group` table and a
`sys_user_group` mapping table.

---

## Thread.currentThread().join() to park main

**Decision**: `NfsServer.main()` uses `Thread.currentThread().join()` to
block indefinitely instead of a spin loop, `sleep(Long.MAX_VALUE)`, or a
`CountDownLatch`.

**Why**: `.join()` on the current thread blocks until the thread is
interrupted. This is clean, idiomatic, and works correctly with JDK 21+
virtual threads — the main thread is a platform thread and parks without
consuming CPU. `sleep(Long.MAX_VALUE)` would also work but is harder to
read. `CountDownLatch.await()` adds an object just for parking.

When Ctrl-C is pressed, the JVM interrupt/shutdown-hook fires, the
`.join()` returns, the `try-with-resources` block closes `NfsServer`, and
`rpcSvc.stop()` drains in-flight operations before exit.

---

## No ACL support

**Decision**: `getAcl()` returns an empty array; `setAcl()` is a no-op.

**Why**: POSIX ACLs (extended attributes on Linux via `getfacl`/`setfacl`)
are file-system specific and require a separate NIO attribute view
(`AclFileAttributeView`) that is not universally supported. NFSv4 ACLs are
a superset. Implementing either correctly requires significant additional
code and database schema changes.

The server signals `AclCheckable.ALLOW_ALL` to nfs4j, which skips ACL
permission checks entirely. All access control is delegated to the
underlying POSIX filesystem permissions (`chmod` bits).

---

## InodeMapper inline limit of 128 bytes

**Decision**: Paths whose UTF-8 encoding is ≤ 128 bytes are stored inline
in the inode handle; longer paths go through a `ConcurrentHashMap`.

**Why**: NFSv4 filehandles have a maximum size of 128 bytes. Short paths
can be encoded directly, avoiding map overhead. The 128-byte threshold is
the hard NFS protocol limit, so it doubles as a natural boundary.

See [inode-mapping.md](inode-mapping.md) for a full discussion.

---

## Path-escape guard in lookup()

**Decision**: `NioVirtualFileSystem.lookup()` calls
`child.normalize().startsWith(root)` and throws if false.

**Why**: Without this check, a client could issue `LOOKUP ".."` from the
root inode, resolve to the parent of `rootPath`, and traverse the entire
server filesystem. The normalisation step collapses `/../` segments before
the prefix check, preventing traversal via dot-dot sequences embedded in
lookup names.

This is a defence-in-depth measure. nfs4j already rejects most malformed
paths at the protocol level, but an explicit server-side guard is good
practice.
